# v1.5 part 4: Smart autoplay, notes

## What the librespot 0.8.0 source does (vendor/librespot-connect, librespot-core from the registry)

- `Session::autoplay()` (core session.rs:586) returns `SessionConfig.autoplay` when it is `Some`,
  otherwise the account's `autoplay` user attribute. Cadence has passed
  `Some(prefs::bool_or("autoplay", true))` since v1.4 (src/player.rs), so the override was
  already on by default; `ConnectConfig` plays no part and was left alone.
- Spirc asks for an autoplay context in `add_autoplay_resolving_when_required` (spirc.rs) when
  fewer than `CONTEXT_FETCH_THRESHOLD` (2) next tracks remain, `session.autoplay()` is true and
  the context uri is not empty. It runs after a load, after every next track, and after a
  context finished resolving. The request is `spclient().get_autoplay_context` with the
  context uri (or the current track as fallback) plus the last 10 played uris
  (`recent_track_uris`) so the server can avoid them. Podcasts are refused.
- `fill_up_next_tracks` moves from the context to the autoplay context after a delimiter when
  repeat is off; with repeat context on it loops with delimiters, so the end (and autoplay) is
  never reached. Repeat one keeps replaying the current track. Shuffle shuffles the whole
  context first; autoplay tracks only follow after the delimiter.
- The next track is preloaded ~30 s before the end, so the first autoplay track is gapless as
  long as the autoplay context arrived before then (it is requested when 2 tracks are left).

## Gaps found in 0.8.0 and fixed in the vendored crate (marked "Cadence patch")

1. Track-list loads (`LoadRequest::from_tracks`: single tracks, search results, Recently played
   cards, artist Popular, sorted/filtered lists, local files) get the context uri
   `spotify:web-api`; that is not empty, so it was sent as the autoplay seed, which the server
   cannot resolve. Now the seed for `spotify:web-api` is the current track (or the latest played
   non-local track). With only local files there is no seed and autoplay is skipped (logged).
2. Refills after the first batch used `ContextAction::Append`, which `fill_context_from_page`
   appended to the *default* context with the context provider. The fill-up had already moved
   to the autoplay context, so those tracks were never played and autoplay stopped after the
   first batch. Appends of type Autoplay now go to the autoplay context.
3. A failed autoplay resolve was put in `unavailable_contexts` and, because of a reversed
   `duration_since`, never retried and never removed. Autoplay failures now back off
   exponentially (5 s, 10 s, 20 s ... capped at 5 min, reset on success) and the map is pruned.
   A retry is also attempted when the next track is preloaded, so a failure on the last track
   gets one more chance before the end.
4. Bounded memory: the autoplay context drops tracks already moved to next_tracks when it is
   refilled; a ring buffer of the last 200 played uris filters repeats. next_tracks (80) and
   prev_tracks (10) were already capped by librespot.
5. Relevance: the server already gets the last 10 played uris. Cadence adds a client-side filter
   (played this session via the ring buffer, tracks of the default context just finished,
   duplicates by uri, already-unavailable uris). Unplayable tracks are still skipped by
   librespot's own `mark_unavailable` on load failure. An autoplay batch that leaves nothing new
   counts as a failure (backoff), so it cannot loop requests.

## Start methods

play / play_from / play_shuffled / session restore use a context uri (playlist, album,
collection, artist) and reach autoplay unchanged. play_list and bare track uris use
`spotify:web-api` and are covered by fix 1. Queue items are in next_tracks, so autoplay is asked
for only when the queue *and* the context are down to 2 tracks. Episodes / shows: no autoplay
(librespot refuses podcasts). Route B not needed: everything goes through spclient's autoplay
call in route A.

## Defaults chosen

- Toggle applies on next launch ("Applies after restart" under it); the session is never
  recreated, so credentials are never touched. Pref key stays `autoplay` in prefs.json.
- Player bar label "Autoplaying similar songs", from the provider of the current track
  (`autoplay`), read through the queue snapshot.
- Ring buffer 200 uris; backoff 5 s doubling, cap 5 min.
- Logs: `autoplay: requested`, `autoplay: resolved`, `autoplay: failed`, `autoplay: skipped`
  lines are written to cadence.log (log crate at info level would need the debug log setting,
  so they go through a small hook Cadence installs).
